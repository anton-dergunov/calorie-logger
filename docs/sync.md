# How synchronisation works

Calorie Logger works completely offline and syncs across devices without a server ever deciding
anything about your log. This is how, and — more usefully — why each piece is the way it is.

The short version: every device holds a full copy of your data and writes to it directly. Changes
are queued, exchanged with the server in one round trip, and merged by a rule that every replica
computes identically. Deletions are recorded rather than performed. Nothing is ever computed on the
server that a device could compute itself.

## The shape of it

```
   iPhone                      your server                     Mac
┌────────────┐              ┌──────────────┐            ┌────────────┐
│ IndexedDB  │  ── push ──▶ │  PocketBase  │ ◀── push ─ │ IndexedDB  │
│  replica   │  ◀── pull ── │   (SQLite)   │ ── pull ──▶│  replica   │
└────────────┘              └──────────────┘            └────────────┘
      ▲                                                       ▲
      └── the UI reads and writes only this ───────────────────┘
```

The interface never waits on the network. Adding a food, editing an entry, reordering a meal, and
resetting the account are all local writes that repaint immediately. The sync engine is a
background process that happens to make other devices agree.

That ordering is deliberate. The app is used standing in a kitchen and sitting on a plane, and an
app that pauses on a spinner because a NAS is asleep is an app that stops being used.

## Every record carries its own history

Five fields travel with each replicated record, alongside its own data:

| Field | Written by | Purpose |
|---|---|---|
| `deleted` | the writing device | tombstone; rows are never physically removed |
| `createdAt` | the writing device | when it first existed |
| `editedAt` | the writing device | its clock at the moment of the edit — the merge key |
| `editedBy` | the writing device | its identity — the tiebreak |
| `revision` | the server | position in this account's change sequence — the pull cursor |

Ids are generated by the client, not the server. That is what lets a food created in airplane mode
be edited, logged against, reordered, and deleted again before any server has heard of it. A
server-assigned id would mean holding a placeholder and rewriting every reference to it later,
which is exactly the class of bug this design exists to avoid.

## Merging: last writer wins, decided the same way everywhere

```
supersedes(incoming, stored):
    if incoming.editedAt ≠ stored.editedAt:  return incoming.editedAt > stored.editedAt
    else:                                    return incoming.editedBy > stored.editedBy
```

Later edit wins. If two devices wrote in the same millisecond, the higher device id wins —
arbitrary, but *consistently* arbitrary, which is the property that matters.

This function exists twice, once in the client and once in the server hook, and the two must stay
identical. Because the rule depends only on the two records being compared, every replica reaches
the same answer without coordinating, in any order, however many times it is applied.

Two details make it hold:

- **Timestamps are strings, compared as strings.** `editedAt` is exactly what
  `Date.prototype.toISOString()` produces, milliseconds included. Lexicographic order on that
  format is chronological order, so no parsing happens on the hot path and no locale can change the
  answer.
- **A device never issues the same instant twice.** Two edits inside one millisecond would be
  indistinguishable, so the client nudges the second one forward by a millisecond. Ordering within
  a device is therefore always total.

Clock skew between devices is real and accepted. A device whose clock is an hour fast will win
merges it arguably should not. The alternative — vector clocks, or a server that orders everything —
costs a great deal of machinery to protect a single-person log where genuine simultaneous conflicts
are close to nonexistent. Losing an edit made on a second device thirty seconds ago is the failure
mode, and it is reported rather than hidden: the sync panel says how many local changes were
replaced by a newer edit from elsewhere.

## The cursor is a sequence, not a clock

Each account has a server-owned counter. Every record the server writes takes the next value in
`revision`, and a device pulls everything with `revision > its cursor`.

It is tempting to use a timestamp instead. That is broken, and quietly: a record written while your
request was already in flight gets a timestamp *before* the moment you finish reading, so the next
pull — starting from that moment — skips it forever. A monotonic counter has no such gap, because
it advances only when something is actually written.

## Deletions are recorded, not performed

Deleting sets `deleted: true`. The row stays.

If rows were removed, a device that was offline during the deletion would come back, see a record
the server does not have, decide it must be new, and push it back. The log would resurrect food you
deleted last week, and it would keep doing it.

So a tombstone is an ordinary record that wins or loses on exactly the same rule as any other edit.
Deleting a food that is in use also tombstones every entry referencing it, in the same commit, on
every device.

## Dataset identity: the trap worth naming

Every reply carries a `datasetId` — the id of the account's sequence row. It identifies *which
database* the cursor is counting in.

Rebuild the database and the sequence restarts at zero. A device still holding a cursor of 4,312
then asks for revisions above 4,312, which the new database has not reached. It pulls nothing.
Everything it holds was already confirmed, so it pushes nothing. It reports itself perfectly in
sync, and shows you a log no other device can see. Silent, and indistinguishable from working.

When the id changes, the client sets its cursor back to zero and marks everything it holds as
pending again — tombstones included, or a deletion would be undone by another device that still has
the record. Then it exchanges again immediately.

**A cursor must never outlive the database that issued it.**

## One round trip

A sync is a single `POST /sync` carrying everything pending and the current cursor, and returning
everything new plus a verdict on each pushed record. Not push-then-pull; both directions in one
exchange, inside one transaction.

Syncing is triggered by a local change (debounced), by the window gaining focus, by coming back
online, and by a timer while the app is visible. Only one runs at a time, and the "syncing" state
is only shown if it takes long enough to be worth mentioning.

On the server, foods are merged before entries, which are merged before settings: an entry's food
relation has to resolve when the entry is saved.

Two things in the reply are less obvious than they look:

- **Rejections are per record.** A record that fails validation is rejected on its own and reported
  back. It must never fail the batch — one bad row that fails the whole push would wedge that
  device's queue permanently, and no amount of retrying would clear it.
- **The reply includes the winners of your own push.** If your change lost a merge, you get back the
  version that beat it, even though its revision may be older than your cursor. Without that, you
  would never receive the record that superseded yours, and you would push the loser again forever.

The client re-runs the same `supersedes` check when applying what it pulled, so an edit made while
the request was in flight is not overwritten by the reply to it. A push is only marked confirmed if
the record is still byte-identical in its merge key; a record edited again mid-flight stays pending.

## Version refusal

`SCHEMA_VERSION` covers the shape of replicated records, and is asserted on every sync. A client
that disagrees is refused the merge outright and told to update.

This is a deliberate refusal, not a failure. A stale device writing the current schema's fields is
how a replicated store gets corrupted, and unlike a single-database app there is no single place to
repair it afterwards. The cost of refusing is one update; the cost of allowing it is unbounded.

Local reads and writes keep working throughout — you can log a whole day on a device that cannot
sync — and the app offers the waiting update as a button rather than an instruction.

When the version does change, a device rebuilds its replica from the server rather than converting
it in place. That is only safe because the server keeps everything, which is why tombstones and the
migration rules are not optional.

## Starting a new device

The default catalogue is seeded when a device's **first successful sync finds the account empty** —
never at startup. A device that is merely offline cannot tell an empty account from an unreachable
one, and guessing would fill a real account with duplicates.

Seeded foods take ids derived deterministically from their names. Two devices that both meet an
empty account therefore produce one catalogue, not two.

Resetting the account is an ordinary local write: tombstone everything, write the catalogue back,
let replication carry it. No server route, no special case, and it works with no server reachable at
all. A catalogue food tombstoned by an earlier reset comes back because its new stamp is later than
the tombstone's.

## What is deliberately not stored

Usage counts and last-used amounts are **derived** from entries, never stored on a food.

Under last-writer-wins, a stored counter would be a field that changes as a side effect of unrelated
activity. Logging a banana on your phone would write the banana record; if you had corrected its
calories on your laptop a moment earlier and it had not synced yet, the counter bump would win on
timestamp and throw the correction away. A field that only ever moves forward is safe to derive and
dangerous to replicate.

The same reasoning bans unique constraints on replicated collections: a uniqueness rule that two
offline devices can both satisfy independently produces a push that can never merge.

Log entries also do not copy a food's name, picture, unit, or nutrition. They reference the food, so
correcting it once updates every day it appears on.

## Durability

The replica lives in IndexedDB. Each write is one transaction across records and their pending
markers together — a crash between the two would lose track of a change that was never uploaded.

If IndexedDB cannot be opened at all, the app falls back to memory and says so in the sync panel. It
still works; it just cannot survive being closed.

## What this is not

- **Not a CRDT.** Foods and entries are small records edited by one person on a handful of devices.
  Last-writer-wins with a stable tiebreak is enough, and a CRDT's metadata would outweigh the data.
- **Not operational transformation.** Nothing here is collaboratively edited in real time.
- **Not server-authoritative.** The server stores and merges records. It does not compute days,
  ordering, totals, or exports — those are the same code on every device, so they cannot disagree.
- **Not a conflict UI.** There is no "which version did you mean" dialog. Merges resolve
  automatically and the count of replaced changes is reported afterwards.
